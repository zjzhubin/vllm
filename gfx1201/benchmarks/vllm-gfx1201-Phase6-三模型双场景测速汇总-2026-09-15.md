### 〇.1 客户端（压测端）调用命令（★ 2026-09-16 补录；原报告只记了服务端命令）

**decode 六档**——每档**单独起一个容器**，`--rate` 在 concurrent profile 下即并发数：

```bash
for C in 1 2 4 8 12 16; do
  docker run --rm --network host \
    -v <results-dir>:/work -v /opt/models:/models:ro -w /work \
    guidellm:phase5k benchmark run \
      --target http://localhost:8012 \
      --model "$MODEL" \
      --processor "$TOK" \
      --backend-kwargs '{"timeout":600}' \
      --profile concurrent --rate "$C" \
      --data /work/datasets/sharegpt_s1_nonce.jsonl \
      --data-samples 32 \
      --data-column-mapper '{"text_column":"prompt"}' \
      --request-type text_completions \
      --request-formatter-kwargs '{"max_tokens":512}' \
      --output-path "/work/results/<OUT>/conc${C}.json"
done
```

**refill（32k/64k/128k @ c1）**：同一条命令，改 `--data` 为长度专用 prompt 文件、`--data-samples 2`、`max_tokens:16`。

**防 prefix 短路（关键设计，非可选）**：数据集 `sharegpt_s1_nonce.jsonl` **每轮重新生成**（带随机 nonce），确保冷 prefill 场景下前缀缓存不命中。refill 臂同样使用唯一随机后缀。

**结果落盘**：`conc{1,2,4,8,12,16}.json`（两遍；第二遍前先把第一遍 `cp` 成 `conc{N}.r1.json`）＋ `refill_{32768,65536,131072}tok_conc1.json`。其中 `args` 字段是 **GuideLLM 自己回填的完整生效参数**——核对实际口径以它为锚，比抄命令更可靠。

> ⚠️ **`--processor` 路径口径不一致（未消解，照抄前必读）**：批1/2/2r/3 的结果 JSON 实录为宿主路径 `/opt/models/<模型>`，批4 与 T125p3 为容器路径 `/models/<模型>`。guidellm 容器只挂了 `-v /opt/models:/models:ro`，宿主绝对路径在容器内**本应不存在**；当时未报错且跑通，机制未查清。**对外引用建议统一采用 `/models/<模型>` 形态，并注明历史批次存在此差异。**
>
> **取证性质说明**：本命令取自本次实际执行的脚本（`s1v3_decode_sweep_6lvl.sh` / `s2v3_refill_3len_c1.sh`），**不是 shell 历史里的手敲命令行**（该机 history 中无 guidellm 记录）。属"本次实际执行形态"，非"当时手打的那一条"。

### 2.3 等效启动命令（逐字）

**场景 A（原始）**：

```bash

  --device=/dev/kfd --device=/dev/dri --group-add video --group-add 991 \

  -e VLLM_ROCM_USE_AITER=1 -e VLLM_ROCM_USE_AITER_UNIFIED_ATTENTION=1 \
  -e VLLM_ROCM_USE_AITER_TRITON_ROPE=1 -e VLLM_ROCM_USE_AITER_LINEAR=1 \

  /opt/venv/bin/vllm serve /models/Qwen_Qwen3.8-27B-FP8 \
  --served-model-name fp8 --port 8012 --tensor-parallel-size 2 \
  --max-model-len 262144 --max-num-seqs 16 --enable-chunked-prefill \
  --max-num-batched-tokens 4096 --gpu-memory-utilization 0.8 \
  --kv-cache-dtype fp8 --enable-prefix-caching \
```

**场景 B（+DFlash2-FP8 草稿 ns=3；mml=98304）**——同上骨架改：`--name w07hb-fp8d`、`-e VLLM_CACHE_SUBDIR=w07hb-fp8d`、`--served-model-name fp8d`、`--max-model-len 98304`，末尾加：


> 场景 B mml=98304 的原因：GMU0.8+草稿下 FP8 权重（27B×1B/卡）挤压 KV 池，mml262144 起服记账失败（可用池 2.4-3.26 GiB 浮动 <需求 4.47 GiB）；96k=经验证可复现口径（v2 复测 READY_OK 163s）。mml 不改 kernel/池，仅改允许最大请求长，数字与 262144 族可比（176128 版对照 Δ≤2.7%）。

## 七、系统发现与生产建议

### 7.1 FP8+dflash 128k refill 静默挂起（⚠ 生产风险）

- 形态：ReadTimeout×2；引擎步进日志静默、kv_cache_usage_perc 反降 0.78→0、token 计数冻结、零错误行
- 对照：FP8 无草稿 128k 正常（2324 tok/s）；cyankiwi+W4A16 草稿 128k 正常（1581）→ **FP8 目标模型+FP8 草稿+长上下文组合特有**
- 生产风险面：生产 qwen36 同组合（GMU0.92/mml262144）长上下文（>96k 请求）存在同风险——建议生产侧长上下文请求路由至无草稿或 INT4 路径，或对 FP8+dflash 限 mml；根治需专项排查（挂账）
- **大池对照验证结果（09-16 p3/pv 双验证，§9.4）**：批1 挂起臂 KV 池 3.26 GiB（GMU0.8/mml96k）；生产大池 7.29 GiB（GMU0.92/mml262144）下 128k 冷 refill **完成（ok=2）、挂起消除**——挂起归属=池容量不足配置而非组合固有缺陷；上述路由/限 mml 建议适用范围收窄为小池配置

### 7.2 KV 池可用量=多因子（非单因子）

- 同 FP8 目标 mml262144：带 FP8 草稿 3.26 GiB vs 无草稿 6.26/6.92 GiB（草稿权重占池）
- INT4+dflash：7.99 GiB（被验）/5.81 GiB（复测，−27%）
- 同配置 boots 间浮动 −26%~−28.5% 且下界无收敛迹象（AOT/cudagraph 记账浮动族）
- 结论：**GMU0.8+mml262144+FP8+草稿=起服记账失败**（需求 4.47>可用 2.4-3.26）；mml 设计须按最坏池+草稿开销；生产 GMU0.92 依赖更大预算+无草稿场景余量充足
- 修正记录：批2「权重精度单因子」表述经 bv 盲区证伪，本报告按多因子口径（台账 P6-351）
